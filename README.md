# ClaudeBugFixes

Client-side tooling that works around Claude Code's duplicate/ghost session bugs (observed on v2.1.235, WSL). Backgrounding, resuming or clearing a session forks it under a new session id, leaving duplicate rows, title-only stub files and un-enterable ghost rows in the agents view and the resume picker. These scripts mark every deletion-safe row so cleanup becomes a glance instead of an investigation.

## Background: where duplicates come from

Session storage (v2.1.235):

- Transcript: `~/.claude/projects/<project>/<session-id>.jsonl` — a fork copies the FULL conversation (all message uuids) into a new file; the per-session `subagents/` folder is NOT copied.
- Jobs registry: `~/.claude/jobs/<first-8-of-session-id>/state.json` — the agents view reads names from here; deleting a transcript does not remove the row.
- Daemon roster: `~/.claude/daemon/roster.json` — live attachable worker processes; cleared on daemon restart.

The three causes of duplicate/ghost rows:

1. Backgrounding or resuming (picker, agents view, parallel window) mints a NEW session id — the same conversation appears as two or more rows, and the original stays under the old id.
2. Title-only stub `.jsonl` files: a shell that never processed a prompt inherits its parent's title — a same-named duplicate row. A dying job can resurrect a deleted filename as such a stub at shutdown.
3. A jobs row with no transcript and a dead worker — an un-enterable "no saved transcript" ghost in the agents view.

## What it does

Two hooks plus a shell wrapper. Append/rename only — nothing is ever deleted, wrong marks self-heal on a later run. **A marker means "safe to delete"** (except the provisional `[Dup?] `); a working non-duplicate session is never marked with a final marker.

| Marker | Meaning |
|---|---|
| `[Old Fork] ` | Transcript superseded by a copy holding the same conversation. Heals when the session diverges past the fork. |
| `[Dup?] ` | PROVISIONAL — probably a duplicate, not yet deletion-verified. Written from roster info alone (a resume-fork spawned after the last completed sweep, parent transcript still present) about 0.3s into the run, before the settle wait, so a fresh fork's row shows its status at once. Job-row name only, never a transcript title. The same run's content sweeps upgrade it to a real verdict or heal it; one that escaped both expires on the next full sweep. Never delete on a `[Dup?] `. |
| `[Dup] ` | Redundant duplicate: an at-rest twin fork of the same parent, a fork shell whose parent conversation another row already carries, or the cold copy of identical same-title twins. Twin-vs-superseded is judged on conversation entries only — junk that Claude Code also gives uuids to (attachments, system-reminder-only user entries, "No response requested." fillers) never turns a twin into an `[Old Fork] `. |
| `[Dead] ` | Job row that can never produce a conversation again: no real transcript and no live or respawnable worker. |
| `[Stub] ` | Transcript with a title but zero messages whose session is unservable — it would open empty. |

A `←` inside a job-row marker (`[←Dup?] `, `[←Dup] `, …) is a best-guess note that the session was minted by backgrounding a live session — the left-press-to-agents-view ghost pattern — rather than by resuming a cold one (judged at provisional time: the parent has a roster entry, or its transcript was written within 5 minutes before the mint; a fork of a session quit moments earlier is mistagged). The tag rides along on marker upgrades, is dropped on heal, never appears on transcript titles, and changes nothing about what the marker means.

On every fork the SessionStart hook also emits a `systemMessage` naming the parent, and renames the parent to `[Old Fork] <title> - forked on <time> by <id>`.

## Name keeping

A rename made in the agents view lands on the job row only; the transcript keeps its old title, so a fork migration or a dying row used to take the name to its grave while the conversation lived on under its automatic title. Three additions close that gap:

- **Row-name sync**: every user-given job-row name (`nameSource: "user"`, markers stripped) is copied into the transcript that backs the row — the row's own session, else its resume target, else the roster launch source — as a normal custom-title append. When several user-named rows back one transcript, one winner is elected deterministically: the row whose own session the transcript is, else an unmarked row over a marked one, else the later roster start time, else the larger folder name — so a fork shell's name never beats the session's own row, and two rows never take turns rewriting the title. Live targets are skipped (same `is_liveish` as everywhere else). A name set from inside a session is never overwritten: an existing custom title is only replaced when it is this tool's own last write (recorded under `~/.claude/fork-watch-name-sync/<session id>`, records kept indefinitely — they must outlive any later rename), a mere echo of the transcript's ai-title, or the short-session-id fallback the sweep itself mints for bare-marker-token titles (a heal or marker append carries no user intent, and the fallback is an unrecorded tool write, not a rename). A marked transcript keeps its verdict; the name lands once the mark heals.
- **Stranded-name rescue**: a fork that dies before its first prompt leaves the user's name on an unservable shell — a judged title-only stub transcript, or a user-named row with no real transcript. The rescue donates the stranded base name to the parent transcript (the one whose continued-in record names the shell; among several record holders an unmarked one beats a merely newer, possibly superseded copy). A dead shell only ever FILLS a name, never replaces one — the parent must carry no custom title beyond an ai-title echo or the tool's own short-id fallback — so wreckage can never outrank a name synced from a living row. A shell custom title that only echoes its ai-title is sweep residue, not a user name, and is never donated.
- **Same-target rows**: several rows pointing at ONE conversation — a pointer row whose `resumeSessionId` names another session, or an alien row whose folder no longer matches its session id — are the same entry twice; renaming or entering the extra one acts on a ghost. The dup sweep groups rows by resume target: the row holding the live worker, else the row that IS the session, else — ranked only by inputs no sweep mutates — an unmarked row, roster start time, folder name. (Never by state.json mtime: the tool's own marker writes bump it, which would swap keeper and `[Dup] ` on alternating runs.) The extra rows get `[Dup] `. Row-level only — the shared transcript is the real conversation and is never marked for this.

## Row repair

The one exception to "append/rename only": a user-named row judged `[Dead] `/`[Stub] ` whose conversation survives in a parent transcript (found through the parent's continued-in record) is repaired in place rather than left as wreckage — its sessionId, resumeSessionId and linkScanPath are repointed at the parent and the marker healed off the name, so the named, enterable entry returns to the agents view. Verified live 2026-10-02: a repointed row respawns and opens the parent conversation. Constraints: only rows with `nameSource: "user"` (unnamed dead shells stay plain deletion candidates), only rows older than the 300s settle window whose session is dead under BOTH roster keys (session id and row folder — they differ after a repair), only unmarked parents (never a superseded copy) that are not live-ish and have been silent for at least an hour (an idle terminal-held CLI session looks exactly like a cold transcript — recent writes are the only tell), never when another servable row already reaches that parent, newest shell wins when several trace to one parent, and the write carries the same mid-flight staleness guard as every other `state.json` write. `is_liveish` also recognizes a live worker by its roster launch source, so a repaired row's running worker keeps its transcript protected everywhere. Brand-new rows are never minted — repair reuses the row the user already named.

## Files

- `fork-watch.sh` — SessionStart hook; also runs standalone as `fork-watch.sh --sweep-only`. Fork detection plus five marker sweeps over the jobs registry (`~/.claude/jobs/*/state.json`), all project transcripts and the daemon roster.
- `fork-watch-end.sh` — SessionEnd hook; marks a session `[Old Fork] ` when its whole conversation lives on in a transcript that is strictly AHEAD of it (holds a conversation message this one lacks). An identical twin is not a successor: twins are judged by the sweep's keeper election, which always leaves one copy unmarked — the end hook marking its own twin could leave every copy of a conversation flagged safe-to-delete.
- `install.sh` — symlinks both hooks into `~/.claude/scripts` and prints the `settings.json` and `.bashrc` blocks to add.
- `tests/fwtest.sh` — fixture test: builds a fake `~/.claude` tree and asserts every marker, heal and stability behaviour (idempotent second run). Real pass/fail assertions with a non-zero exit on any mismatch, and live-worker fixtures that borrow the test shell's own pid and `/proc` starttime — so the dead-pid-only blind spot that once hid a broken `pid_matches_start` (every recorded worker read as dead, disabling all live-session protection) cannot reopen.
- `tests/staletest.sh` — unit test for the write-race guards in `set_job_marker` and `repair_job_row`, plus `rename_parent`'s titleless short-id fallback; run `fwtest.sh` first (it builds the fixture tree).
- `tests/endtest.sh` — fixture test for the SessionEnd hook: supersede marking, the junk-tail retry, the no-successor guard, the twin and junk-ahead-twin non-successors, the malformed-id guard, the titleless fallback. Self-contained.
- `DOCTRINES.md` — the doctrine-by-site audit matrix: every safety rule against every place it must hold. Check new sweeps, elections and writes against it.

## Install

```
./install.sh
```

Then add the two printed blocks (hook registration in `~/.claude/settings.json`, `claude()` wrapper in `~/.bashrc`). The wrapper matters: the agents view and the resume picker read names **once at open**, so the sweep must run synchronously before launch — a hook started in parallel loses that race.

## Design notes

- Everything loads once per run into bash caches (one jq for the roster, one jq+stat for all job files, one grep/awk/jq pipeline for all titles) — per-file spawns cost ~10s on WSL before this. Current costs on a ~100MB tree: ~40ms when nothing changed since the stamp, ~0.5-0.8s when something flushed, ~2s only when the stamp is missing entirely (first install).
- Content-driven verdicts (copy-dup groups, divergence heals) are skipped for anything not written since the last completed sweep — those verdicts depend only on file contents the previous sweep already judged. Time- and roster-driven checks still run every sweep. On a ~100MB tree this cuts a steady-state sweep to well under a second.
- Same-title groups are judged via a containment matrix: one `grep -oF -f` per file with every sibling tail uuid as a pattern, instead of n² pairwise greps. Divergence heals batch the same way — one grep per project with every marked tail as a pattern, instead of one full-directory grep per marked file.
- The junk-tail fallback reads from the file's end (`tac | jq --unbuffered | head -1`), so its cost is the junk-tail length, not the file size.
- Loader field separators are US `0x1f` (`jq --arg us $'\x1f'`), not tabs — tab is IFS whitespace, so empty fields would collapse and shift columns.
- The sweep stamp carries the run's judgment time (its NOW snapshot), not the finish time, so "since the stamp" windows (the settle and hour-silence crossings) never miss what crossed during the run itself. A run that lands any write also voids its own later skip gates (rescue, repair) via a dirty flag — the tool's writes restore idle mtimes on purpose, so a [Stub]/[Dead] verdict minted this run would otherwise be invisible to the mtime-only gates running moments later.
- A sweep stamp under 30s old skips the sweeps — but only when nothing was written since the stamp (one cheap stat pass over project dirs, transcripts, jobs and the roster). A flush or rename after the stamp voids the skip, so marks still land on the very first open after a write ends; live sessions' own writes are exempt from voiding it, since a live row is never marked. Same-second writes count as newer (mtimes are whole seconds), at worst costing one redundant sweep.
- `state.json` writes abort when the file's `%.Y` mtime changed mid-flight, so a concurrent daemon rename is never clobbered — and the staleness token is always stat'd BEFORE the name is read, so a rename landing between read and token can't slip under the guard.
- Liveness is judged under BOTH roster keys everywhere it can mark or move a name — the roster is keyed by the row folder, which stops matching the session id after a row repair or an alien migration, so the dead sweep, the rescue, the stub judgment and the elections all check the folder key too. A row whose worker is live right now never GAINS a final deletion-safe mark, even as the redundant one of two live twins.
- Copy-dups are judged before the name sweeps (renaming first would split a same-title group before judgment and silently lose the duplicate verdict), and any title written this run voids the copy-dup group skip: heals land in the transcript sweep and are re-judged the same run. A name landed by sync or rescue can also JOIN its transcript into another same-title group holding the same conversation — a membership nothing had judged, and one no later run would see, since the append restores idle mtimes and the group skip yields only when a group member is written. So whenever the name sweeps land anything, the copy-dup judgment runs a second time; it is idempotent, every earlier verdict already landed, and the renames only touched unmarked keepers.
- Daemon JSON that jq 1.6 cannot parse — a lone-surrogate `\udXXX` escape, minted when a well-formed JSON writer truncates display text mid-emoji — is retried with the surrogate escapes stripped, on every read and write of `state.json` and `roster.json`. Without the retry such a row would be silently exempt from every marker, heal and repair forever, and one bad escape in the roster would void all live-session protection at once.
- The cache loaders flatten newlines, carriage returns and the field separator out of names and titles, so a multi-line row name can no longer shear a loader record and leave its row silently exempt from every sweep; an empty custom-title entry reverts to the automatic title in the cache exactly as the live reader always treated it. The live title readers flatten the same way (a newline-bearing title otherwise read as its last line only), and a title line MISSING its field is ignored by cache and live readers alike — only a present empty string means revert.
- `state.json` rewrites copy the file's own mode onto the tmp file before the atomic rename — the shell's umask would otherwise loosen a 0600 daemon row to world-readable on its first marker write. A sweep stamp sitting AHEAD of the clock (a clock step back after sleep) counts as "never swept" rather than suppressing every sweep until real time catches up.
- A row-level `[Dup] ` OR `[Old Fork] ` whose transcript title no longer carries any marker is healed by the dup sweep: an in-session rename (or a heal whose row half aborted on a daemon race) dissolves the verdict that justified the mark, and no other sweep revisits materialized rows — without the heal, a deletion-safe mark would sit forever on a session the user just claimed. Every copy of the session's transcript is judged (it can sit in a second project directory); one still-marked copy keeps the row's verdict. Rows with no transcript at all stay with the dead sweep.
- Deleting a transcript moves no surviving file's mtime, so the content gates fold the project DIRECTORY's mtime in — otherwise deleting the keeper or superseder of a marked copy left a deletion-safe mark sitting on the only remaining copy of the conversation until some unrelated write. Deletion, creation and rename all move the directory mtime.
- A roster file that exists but cannot be parsed (even after the surrogate strip) fails CLOSED: every live-session protection reads through the roster, so rather than judging with every worker apparently dead, the run skips all sweeps and writes no stamp. Hook-mode fork detection still runs — it degrades to the roster-free uuid heuristic.
- A `[Dead] `-prefixed TITLE on a real transcript heals like a wrong `[Stub] `: the dead verdict is row-only, so a marked title can only be inherited text (Claude Code seeds a fork's ai-title from the marked row name it was launched from).
- Crash-torn files are read and written safely: every reverse read guarantees a final newline first (a glued last line would silently drop the newest conversation entries and misjudge a diverged file as a twin), and every title append terminates the file before writing (a glued title corrupts the last entry and hides the verdict from the scanners forever). The newline repair runs only when the last byte is actually missing its newline — an intact file keeps the plain reverse read's stream-from-the-end cost.
- A present-but-zero-byte roster counts as unreadable and fails closed like a corrupt one — it is the torn truncate-then-write state, and an empty-but-real roster is `{"workers":{}}`, never 0 bytes. A missing roster file stays "no daemon" (fail open) on purpose.
- An existing-but-unreadable transcript counts as real: permission damage moves no mtime, so nothing would ever revisit the `[Dead]` it used to cause.
- Row verdicts are always backed by title verdicts, in write order too: the fork handler and the end hook write the title first and the row only on success, so a failed rename or append can never strand a row-only mark that no heal revisits. Only session-shaped ids (hex and dashes) may touch a row at all, and stray files next to the transcripts (a manual `<sid>-copy.jsonl` backup) join no duplicate judgment whatsoever — as a group member such a file could win the keeper election by mtime, or even read as "ahead", and put the deletion-safe mark on the REAL session while the backup kept the name.
- A transcript-derived verdict lands only on the row that actually serves that session: when a row's `sessionId` names a different session (the shape a row repair or an alien migration leaves), both hooks refuse the row write — otherwise a verdict on the folder's OLD transcript would mark a row, possibly live, that serves someone else. Heals stay unrestricted.
- A project directory that exists but cannot be read and searched fails the whole run CLOSED (no sweeps, no stamp), like a corrupt roster: every transcript in it drops out of the file patterns, and "no transcript" is a load-bearing signal — without the guard, permission damage on one directory puts deletion-safe `[Dead]` on rows whose conversations exist.
- Only an UNMARKED sibling counts as holding a marked file's conversation in the divergence heals: a set of copies that only hold each other's tails — two marked copies whose unmarked keeper was deleted, sitting in different title groups where the copy sweep can never re-elect — heals instead of sitting deletion-safe forever with no unmarked copy left.
- Every title this tool can mint is recognizable later as its own replaceable write: sync/rescue names are recorded, markers are skipped while present, and every fallback base is the 8-char short session id (never a minted phrase, which would read as a human name after a heal and block row-name sync forever). The full rule-by-site audit lives in `DOCTRINES.md`.
- Transcript title appends restore the file's mtime when it was idle, because `claude --continue` resumes by recency; hot files are never backdated. Because a file idle under 60s keeps the bumped mtime, the identical-twin keeper election ranks "unmarked before newest" — otherwise marking a young twin would crown it keeper on the next run and the `[Dup] ` would alternate between the pair forever.
- Heals strip only the exact `- forked on HH:MM dd.mm.yyyy by xxxx` suffix shape this tool mints — a user-chosen name that happens to contain `" - forked on "` survives marking and healing intact.
- Live sessions are never marked, and there is no recency window: a file written in the last 5s is polled every 100ms and judged once settled — daemon flushes are sub-second bursts triggered by the same keypress that starts the sweep, so waiting them out lets marks land on the first open without ever reading a half-written file. Each file settles on its own: quiet for 3 consecutive polls is settled and re-scanned; changed on 5 polls is a genuinely streaming session, skipped for that run immediately so one active session never stalls the sweep to the 3s cap.
- Claude Code seeds a forked session's ai-title from the parent's displayed name, so marker text can leak into a new session's title; a base that is only a bare marker token is replaced with the short session id.
- Whenever a file's raw tail uuid matches no sibling — always the case when the tail is junk minted in that file alone — duplicate verdicts, marker healing and the session-end supersede check all fall back to the last conversation uuid, so junk can neither hide a duplicate nor cause heal/re-mark churn.

## Cleanup recipe

The scripts only mark; deletion stays manual. Removing a row for good needs BOTH the transcript file and the `~/.claude/jobs/<first8>/` dir gone (or Ctrl+X twice in the agents view). A row with a live roster worker survives until the daemon restarts. The resume picker lists transcript files by recency — a leftover file keeps its row regardless of the registry.
